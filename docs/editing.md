# Как изменять календарь

Каталог имеет `schemaVersion: 1`. Редактируемые сущности хранятся отдельно; при сборке проверяются связи и формируется самостоятельный `index.html`.

## Где находятся данные

| Каталог                                 | Содержимое                                                                |
| --------------------------------------- | ------------------------------------------------------------------------- |
| `data/products/`                        | Общие карточки: постоянный `id`, имя, отделы `productTypes`, общие советы |
| `data/variants/`                        | Страна, категория, сорт, псевдонимы и связи конкретного варианта          |
| `data/seasons/`                         | Календарь варианта, пояснения, основания и дата исследования              |
| `data/advice/`                          | Общие и условные советы, шаги, условия хранения, статус публикации        |
| `data/evidence/`                        | Утверждение, подтверждающие источники, область применимости и ограничения |
| `data/sources.json`                     | Реестр публикаций и ссылок                                                |
| `data/taxonomy/`                        | Происхождения и категории с постоянными ID                                |
| `data/migrations/legacy-favorites.json` | Соответствие прежних `r…` постоянным ID продуктов                         |

Коллекции поддерживают несколько JSON-файлов с массивами. Название файла не является идентификатором сущности. Идентификаторы назначаются один раз: не изменяйте их при правке названия, сорта или категории.

## Добавить вариант существующего продукта

1. Найдите `productId` в `data/products/catalog.json`.
2. Выберите `originId` и `categoryId` из справочников. Новое происхождение добавляется в справочник вместе с `navigationGroup`; редактировать JavaScript не требуется.
3. Добавьте вариант с новым ID и `seasonProfileId`. Список `adviceIds` содержит только дополнения к общим советам продукта, `adviceOverrides` — явные замены.
4. Добавьте сезонный профиль, указывающий тот же `variantId`, и основания в `data/evidence/`.
5. Проверьте область применения общих советов: новый вариант должен входить в `scope.variantIds` соответствующих оснований. Не расширяйте её, если источник неприменим к новому сорту.

Для нового продукта сначала добавляется самостоятельная запись продукта с `productTypes: ["vegetable"]`, `["fruit"]` или `["berry"]`, затем хотя бы один вариант. Можно указать несколько разных типов: например, `productTypes: ["vegetable", "berry"]` для томата. Первый элемент — привычный основной отдел, последующие — дополнительные поисковые отделы. Этот порядок задаёт приоритет в поиске: при выборе «Ягоды» томат выводится после основных ягод. Список не зависит от страны и `categoryId` варианта. Например, клубника остаётся ягодой как для российских, так и для импортных вариантов. Не добавляйте вариант как ещё одну карточку с тем же названием. Основания для текущих 91 продукта и правила выбора дополнительного типа — в [проверке отделов поиска](product-type-audit.md).

## Календари

Текущие профили используют `representation: "legacy-monthly"`: сохранённые редакционные оценки на 12 месяцев. Значения `p/g/b/h/t/n/u/a` имеют прежний смысл. Сезон связан с доказательствами через `evidenceIds`; списки источников собираются из оснований.

Исторический месячный код не превращается автоматически в научный факт о сборе, хранении или пике вкуса. Новое представление сезонных фактов потребует отдельного контракта и обработки в `resolveSeason()`. Пока редактируйте подтверждённые месячные оценки, их пояснения и ограничения.

Не заменяйте `u` на `n` из-за отсутствия источника. Промышленная лёжкость не доказывает сохранность конкретной партии.

## Советы

Один совет — одна сущность с ID, `productId`, `topic`, `summary`, `steps`, `appliesTo`, `editorialStatus`, `reviewedAt` и `evidenceIds`.

Разделы: `choose`, `ripen`, `store`, `prepare`, `freeze`, `discard`. Их русские заголовки находятся в `content/ru.json`.

Общие сведения задаются как `appliesTo: { "kind": "general" }`. При миграции существующие абзацы сохранены общими: их внутренние оговорки не были автоматически превращены в точные правила. `reviewedAt: null` означает, что отдельная дата проверки совета не установлена.

Условный совет должен явно описывать условия:

```json
{
  "kind": "conditional",
  "form": "cut",
  "readiness": "ready",
  "environment": "home"
}
```

Допустимые формы: `whole`, `cut`, `prepared`, `any`. Состояния: `firm`, `ready`, `any`. Среда: `home`, `commercial`. При неизвестном состоянии точный совет попадает в `needsContext`, а не применяется молча. Экран подробностей передаёт домашнюю среду, форму покупки и выбранную спелость. Устройство интерфейса и границы данных описаны в [purchase-advice.md](purchase-advice.md).

Советы без повторения подключаются по ID: общий — через `product.adviceIds`, особый — через `variant.adviceIds`. Замена задаётся объектом с `replacesAdviceId`, `withAdviceId`, `reason`. Сборка обнаруживает конфликты, отсутствующие ссылки и советы другого продукта. Черновая замена не скрывает опубликованный совет.

`editorialStatus: "draft"` позволяет подготовить проверяемую структуру до публикации. Только `published` попадает в советы пользователю. `retired` сохраняет выведенную из использования запись. Черновики не являются секретными: текущий самостоятельный HTML содержит весь каталог. Не помещайте в данные личные или закрытые заметки.

## Условия хранения

Необязательное поле `storage` содержит `place`, `temperatureC`, `duration`. Каждое значение явно имеет один из статусов:

```json
{ "status": "unknown", "reason": "Подтверждённого режима пока нет" }
```

Для известного места используется `value: "room"`, `"refrigerator"` или `"freezer"`. Для температуры — `value` с `min` и `max` в °C.

Известный срок требует диапазона `min/max`, единицы `hour/day`, точки отсчёта `purchase/cutting/ripeness/harvest`, значения `quality-estimate/safety-limit` и непустого списка `conditions`. Это структурированные поля, а не числа, извлечённые из свободного текста.

Срок безопасности требует соответствующего источника и отметки `supports: ["food-safety"]` у основания. Отметка не заменяет редакционную проверку применимости источника. Оценка вкуса или свежести не является сроком безопасности. Численные рекомендации всегда проверяются вместе с условиями.

## Избранное и состояние

Новые избранные карточки сохраняются под постоянным `productId` в `moscow-season-preferences-v3`. При первом чтении прежние `r…` преобразуются по таблице миграции. Старое хранилище остаётся нетронутым; неизвестные исторические ID сохраняются. Более новая версия настроек не перезаписывается старым кодом.

`FilterState` хранит значения экрана независимо от DOM. Элементы формы отправляют изменения, отрисовка читает состояние. Для будущих ссылок и восстановления фильтров следует использовать тот же объект состояния, а не читать формы из разных модулей.

## Где менять код

- `src/domain/catalog.js` — индексы и неизменяемый каталог.
- `src/domain/advice.js` — применимость и явные замены советов.
- `src/domain/seasons.js` — сезонная оценка.
- `src/domain/product-groups.js` — выбор представителя по постоянному ID продукта.
- `src/application/` — подготовка моделей списка и подробностей.
- `src/components/` — отображение готовых моделей. Здесь не выбираются страна, совет или источник.
- `src/state/` — состояние экрана; `src/services/` — браузерные зависимости.
- `scripts/lib/validate-data.cjs` — проверка структуры и связей при сборке.

## Проверки

```sh
npm run format
npm run build
npm test
npm run test:browser
```

`index.html` включается в изменения вместе с исходниками. Проверки содержат сценарии миграции избранного, конфликтов советов, неизвестного состояния покупки и сортовых исключений.

`scripts/verify-v6-migration.mjs` и контрольные суммы в `docs/migrations/` сохранены как архив проверки переноса версии 5. На текущем каталоге этот скрипт не проходит: после миграции данные редактировались. Для проверки нынешнего состояния используйте команды выше.
